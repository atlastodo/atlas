# AGENTS.md

## Working with the user (standing instruction)

- Before planning work on a bug, ask questions until the bug is properly understood (symptoms, reproduction, expected vs actual).
- Also ask questions about the proposed solution before implementing — don't assume intent.

## Dev environment

- This is Atlas core (`atlastodo/atlas`): the server, the Rust client and CLI, and the core JS packages. The todo app (`apps/mobile`, `apps/electron`, the landing site) lives in `atlastodo/atlas-todo`, with its own devenv, CI and releases; app work happens there.
- All dev commands (`dev`, `nix:bun-lock`, `test:all`, `lint`, `fmt`, `db:migrate`, `db:reset`, `version:bump`, `packages:pack`) are devenv scripts defined in `devenv.nix` — run them inside `devenv shell`. The root `package.json` has **no** scripts; there is no root npm/bun task runner. (The full-suite script is `test:all`, not `test`: a script named `test` collides with the shell builtin and `devenv shell test` silently no-ops.)
- Bun is the package manager (`bun.lock` committed; CI installs with `--frozen-lockfile`); Node 26 is the runtime (devenv, `engines`, CI). Bun is pinned to **1.4.2** in devenv (via the nixpkgs snapshot in `devenv.lock`) and `BUN_VERSION` in `.github/workflows/*.yml` — bump them together. The Docker image no longer uses Bun.
- Postgres runs as a devenv service: `devenv up`. Dev DB `atlas_dev`, test DB `atlas_test`, user/password `atlas`/`atlas`.
- `DATABASE_URL`/`TEST_DATABASE_URL` are derived from the port devenv actually allocated (`$PGPORT`), which may not be 5432. Keep DB config out of `.env` — it auto-loads and would shadow the derived URLs.
- The server refuses to start without `DATABASE_URL` + `JWT_SECRET`; copy `.env.example` to `.env`.
- `dev` runs the server with cargo watch on :8080 and serves the pinned web build (`nix build .#web-dist`) unless `STATIC_DIR` is set.

## Verification

- `test:all` = full suite, in order: `cargo nextest run --workspace` → vitest in `packages/client-core`, `packages/shared` and `packages/sdk`, under `set -euo pipefail` (the first failure stops it). `crates/atlas-server/tests/*` are integration tests that need Postgres up (they migrate `TEST_DATABASE_URL` themselves); `atlas-core` tests are Postgres-free.
- `lint` = `cargo fmt --check` + clippy (`--no-deps -D warnings`, as in CI) + `tsc --noEmit` for every core package (`bun run --filter '*' typecheck`, as CI's `Lint (TypeScript)`) + `oxlint .` (`.oxlintrc.json`: the rules of typescript-eslint recommended, which ESLint ran until TypeScript 7, whose npm package has no JS compiler API for typescript-eslint) + `prettier --check .` (`.prettierrc.json`, `.prettierignore`) + the licence check + the `nix/bun.nix` freshness check. `fmt` runs `cargo fmt` and `prettier --write .`.
- Runners are per-package, deliberately separate (not `bun test`):
  - Rust: `cargo nextest run -p atlas-server <name>` for one test. Every server test shares one database (`TEST_DATABASE_URL`), so a test that runs a database-wide sweep (op retention, blob GC, account purge) and asserts on what it removed must be listed in the `database-sweeps` group in `.config/nextest.toml`, which runs them one at a time; otherwise they delete each other's rows and flake.
  - `packages/*`: `cd packages/shared && bunx --bun vitest run src/foo.test.ts` (vitest runs under Bun's runtime, supported since Bun 1.4; `test:all` and CI do the same).

## Layout

- `crates/atlas-core` — pure Rust domain logic (HLC and op log types), no I/O. Conflict resolution, recurrence and the task rules live in TypeScript (`packages/client-core`, `packages/shared`) for the apps and are ported to Rust in `crates/atlas-client` for the headless tools; the JSON fixtures in `test-vectors/` are read by both, and a rule change needs a fixture both sides pass.
- `crates/atlas-client` — the Rust client core (crypto, API-token session, sync, store, task rules) at test-vector parity with `packages/client-core` and `packages/shared`; `crates/atlas-cli` — the `atlas` CLI on it, released as static `atlas-X.Y.Z-<target>` binaries (musl on Linux, for Alpine-based images such as n8n). Its output is pinned by `test-vectors/cli_golden.json` (`GOLDEN_UPDATE=1` re-records it, sorting every object's keys: re-record only new scenarios and keep the rest of the file as it was). A session syncs one app (`ConnectOptions::app`, sent as `x-atlas-sync-apps`); `atlas journal entries …` opens a journal session (`crates/atlas-client/src/journal.rs`, entry schema in `docs/integrations.md`), `atlas vault …` a vault session (`crates/atlas-client/src/vault.rs`; its item rules are `packages/shared/src/vault.ts` too, held together by `test-vectors/vault_item_vectors.json`; the SDK's `VaultClient`).
- `crates/atlas-secretspec` — `secretspec-provider-atlas`, an external SecretSpec provider (the Secret Provider Protocol of SecretSpec 0.21+, through the Apache-2.0 `secretspec-ipc` crate) over a vault session: project/profile/key are folder/item/field. Released next to the CLI as `secretspec-provider-atlas-X.Y.Z-<target>`. Its e2e tests launch the binary over the protocol against a real server; `the_secretspec_cli_resolves_vault_secrets` is `#[ignore]`d and needs `SECRETSPEC_BIN` (a secretspec 0.21+ binary; devenv 2.4 ships one) and `cargo build -p atlas-cli`. `ATLAS_E2E_SERVER` points the tests at a running server instead of an in-process one (raise its `AUTH_RATE_LIMIT_MAX`: the tests sign in many times). See `docs/integrations.md` (SecretSpec).
- `manifests/<app>.json` — the suite's app manifests (entity kinds and their plaintext fields), the single source of truth for which fields stay unencrypted: compiled into the server by `atlas-core` (`manifest.rs`, `Registry`) and bundled by `packages/client-core` (`fieldPolicy.ts`). Todo's kinds keep bare wire names; any new app's kinds must be `<app>.<kind>` and be added as `EntityKind` variants (a test checks both agree). A manifest's `api_tokens` policy (expiry required, longest lifetime, read-only by default; the vault sets all three) is enforced by the server for every token that includes the app (`check_token_access` in `auth/api_tokens.rs`, read-only in `AuthUser`); `test-vectors/field_policy_vectors.json` pins both the plaintext fields and the policies for Rust and TS. Instances choose apps with `ATLAS_APPS`; accounts with `account_apps` (`/auth/apps`). `GET /discovery` is the public server/app/capability probe. See `docs/architecture.md` (Apps and manifests).
- `crates/atlas-server` — Axum + sqlx over Postgres. `migrations/` is the schema source of truth.
- `packages/client-core` — local SQLite/IndexedDB store + sync client; `packages/shared` — portable pure TS logic (and the UI i18n catalogs the app uses).
- The core JS packages (`@atlastodo/client-core`, `@atlastodo/shared`, `@atlastodo/sdk`) are publishable and are what the app repository consumes, as pinned versions: `scripts/build-core-package.mjs` (`bun run build`) writes `dist/` (Bun-bundled ESM + tsc declarations), copies the `test-vectors/` files named in `atlas.testVectors` (gitignored copies; a test fails when a package's tests read one not listed) and the licence; `packages:pack` (`scripts/pack-core-packages.sh`) packs them with `bun pm pack`, never `npm pack` (only Bun rewrites `workspace:*`). In this repo they are used unbuilt through the `@atlastodo/source` export condition (the packages' `vitest.config.ts` aliases) — a new entry point needs it too. `scripts/smoke-core-packages.sh` checks the tarballs as a consumer would (CI). A change to their API is a breaking change for the app: it picks it up with the next core release.
- `packages/sdk` — headless client for integrations: signs in with a personal API token (`atlas_pat_…`, made in Settings → API tokens), unwraps the account keys the token carries and syncs into memory; reuses the `packages/shared` task rules. The `atlas` CLI is the Rust one in `crates/atlas-cli`. Token sessions are refused on account-critical routes (`InteractiveAuthUser`). See `docs/integrations.md`.
- `apps.lock.json` — the pinned web build of the todo app (`todo`: version, URL and SHA-256 of a `atlas-todo-web-X.Y.Z.tar.gz` release asset of `atlastodo/atlas-todo`, plus that release's `THIRD_PARTY_NOTICES.txt`), set with `node scripts/pin-app-web.mjs X.Y.Z` (checks both against the release's `SHA256SUMS.txt`). `docker/Dockerfile` reads it (or explicit `TODO_WEB_*` build args) and the flake's `web-dist` fetches it; nothing here builds the app. Moving the pin is a reviewed commit. The history of the split is `docs/repo-split.md`.
- Self-hosting: the root `compose.yaml` (project `atlas-todo`) only `include:`s `docker/docker-compose.yml`; run compose from the root so it reads the root `.env`. Server settings and defaults come from `crates/atlas-server/src/config.rs` (+ `ratelimit.rs`), mirrored in `.env.example` and `docs/self-hosting.md` — keep all three in step. The NixOS module mirrors no defaults: its `settings` passes env names through, and its first-class options, the reserved-name list and the socket `DATABASE_URL` form (validated against a live server) must track `config.rs`.
- The root flake builds `atlas-server` from source (derivations in `nix/packages/`, also exposed as `overlays.default`) and provides `web-dist`, the fixed-output fetch of the `apps.lock.json` todo pin, which is what a `services.atlas.staticDir` points at. `nixosModules`: `services.atlas` as `atlas`/`server`/`default`, with the pre-rename `services.atlas-todo` option and `nixosModules.atlas-todo` kept as deprecated aliases (checked by `server-module-rename-eval`). The desktop package and its NixOS/Home Manager modules moved to the app repository's flake. `nix flake check` builds everything and runs the `server-vm` NixOS VM test (`nix/tests/server.nix`; needs KVM). No flake build reads `nix/bun.nix` any more; it and the `bun2nix` input stay so `nix:bun-lock`/`lint`/`dependabot-bun-nix.yml` keep working: run `nix:bun-lock` after every `bun.lock` change (`lint` fails when it is stale).
- `docs/` holds the operator, architecture, integration and release guides (`self-hosting.md`, `architecture.md`, `integrations.md`, `releasing.md`).
- The pre-sync REST entity CRUD (task/project/section/label endpoints over the relational tables) was removed on 2026-09-21: the client data path is the sync op log exclusively. What remains of `projects.rs` is the E2EE key-distribution routes (`PUT /projects/:id/keys`, `PUT /projects/:id/member-keys/:member_id`, `GET /project-keys`, `GET /project-keys/missing`); membership/invites (`members.rs`) are unchanged. The relational `tasks`/`projects`/`sections`/`labels`/`task_labels` tables are dropped by `20260926000026_drop_orphaned_entity_tables.sql`; their creating migrations stay (append-only history). `project_members`, `project_keys` and `blobs` keep `project_id` as a bare UUID with no foreign key.

## CI & release (GitHub Actions)

- CI is `.github/workflows/`. Default branch is `main`; pre-releases are cut on the long-lived `dev` branch (see below). Commit messages follow Conventional Commits (`feat:`, `fix(server):`, …). A commit that fixes an issue puts `Fixes #N` (one line per issue) in its body: PRs target `dev`, where GitHub ignores closing keywords, so the keyword must travel with the commit and closes the issue when it reaches `main` with the next stable release. Don't rely on the PR description for this.
- `ci.yml` runs on push to `main`, on PRs, and when `release.yml` or `dev-image.yml` calls it. Jobs (check names): `Lint (Rust)`, `Lint (TypeScript)`, `MSRV` (Cargo `rust-version`, 1.94), `Test (Rust)` (Postgres 16 service), `Test (TypeScript)` (the three packages' vitest, then the packed tarballs smoke-installed), `Audit (Rust)` (cargo-deny), `Audit (JS)` (`bun audit`). A `changes` job picks the jobs by changed paths: Rust jobs for `crates/`, `migrations/`, `Cargo.*` (and `manifests/`, `test-vectors/`); TS jobs for `packages/`, `package.json`, `bun.lock`, `test-vectors/`, `manifests/`; Lint (TypeScript) for anything outside the Rust tree (Prettier covers docs). The audits and MSRV run when manifests or lockfiles change and weekly (Monday cron); a tag, a manual run or a release runs everything. A newer push cancels the running one. Branch pushes whose head commit starts with `chore(release):` skip CI; the tag run tests that commit.
- Dependabot (`.github/dependabot.yml`): weekly version updates for Actions, Cargo, Bun and Docker, grouped minor/patch, targeting `dev`. Security updates are on as a repo setting and always target `main`: merge one there, then merge `main` back into `dev`. Dependabot doesn't update `nix/bun.nix`; `dependabot-bun-nix.yml` regenerates it on its bun PRs and pushes to the PR branch. The pinned web build in `apps.lock.json` is not a Dependabot ecosystem: move it by hand with `scripts/pin-app-web.mjs` when the app releases.
- `scripts/third-party-licenses.mjs`: `--check` (in `lint` and `Lint (TypeScript)`) fails when a shipped JS package (the `dependencies` closure of the core packages) has a licence outside its allow-list, which mirrors `deny.toml`; `--notices` writes `THIRD_PARTY_NOTICES.txt` (the server's and the CLI's crates plus those JS packages), which `docker.yml` puts in the image and the release attaches. The web app's notices come from its release, pinned in `apps.lock.json`: the image carries them as `/usr/share/doc/atlas-todo/web/THIRD_PARTY_NOTICES.txt`. `scorecard.yml` runs OpenSSF Scorecard on `main` and weekly.
- The two audits are `continue-on-error` on purpose (informational). Fixable advisories go in `overrides` or a dependency bump, never an ignore list.
- Branches: work lands on `dev`; `main` is stable-only. A plain push to `dev` publishes only the moving `dev` Docker tag (`dev-image.yml`: CI for the changed paths, then the image on GHCR and the Docker Hub mirror; skipped for `chore(release):` commits and docs-only pushes); nothing else is published without a tag. Cut a pre-release by hand on `dev`: `version:bump X.Y.Z-rc.N`, commit `chore(release): vX.Y.Z-rc.N`, tag, push `dev` and the tag. `main` takes no direct pushes (ruleset "main: PRs only": a PR from `dev`, merge commits only, CI required, no bypass). To ship: on `dev`, `version:bump X.Y.Z` and commit `chore(release): vX.Y.Z`; open a PR `dev` → `main` and merge it; tag the merge commit on `main` `vX.Y.Z` and push the tag; then fast-forward `dev` to `main`. There is no dev server; app.atlastodo.dev stays on stable releases. Full runbook: `docs/releasing.md`.
- Versioning is lockstep: never hand-edit a version in one manifest. Use `version:bump [--no-notes] <x.y.z|x.y.z-rc.N|patch|minor|major>` (updates all package.jsons, `bun.lock`, Cargo manifests, regenerates `nix/bun.nix`, and regenerates `RELEASE_NOTES.md` when the version changes (a stable release lists commits since the last stable tag, so it carries what its rcs did; an rc lists commits since the last tag of any kind); `--no-notes` skips that). Only `X.Y.Z` and `X.Y.Z-rc.N` are accepted (`patch|minor|major` need a stable current version). The app has its own version line and Android versionCode in its repository.
- A `v*` tag runs `release.yml`: `CI` → `Prepare` (in the `release` environment; the tag must equal the package.json version; extracts the notes) → `Docker` (the reusable `docker.yml`, shared with `dev-image.yml`): `Third-party notices`, then `Docker image (<arch>)` per architecture (the web stage downloads and sha256-checks the `apps.lock.json` todo pin and its notices), pushed by digest (arm64 only when the repo is public: its hosted runners are free only there; per-arch `buildcache-<arch>` tags) → `Docker image` merges them into the multi-arch `ghcr.io/<owner>/<repo>` with the OCI metadata from `IMAGE_METADATA`, and mirrors it to Docker Hub as `vars.DOCKERHUB_IMAGE` when that and the `DOCKERHUB_*` secrets are set and the repo is public; plus `CLI` and `Core packages` (the three `atlastodo-<pkg>-X.Y.Z.tgz`) → `GitHub Release` → `npm publish` (trusted publishing when the `NPM_TRUSTED_PUBLISHING` variable is `true`, else `NPM_TOKEN`: a prerelease under `next`, provenance only from a public repo; a failed publish never blocks the release, re-run that job). `IMAGE_ALIASES` (or docker.yml's `image-aliases` input) tags the image under extra GHCR/Docker Hub names (`ghcr.io/atlastodo/atlas-todo docker.io/atlastodo/atlas-todo` during the rename's deprecation period). Secrets and variables are listed in `docs/releasing.md`. A tag containing `-` is a prerelease: a GitHub prerelease (`--latest=false`), Docker tag `X.Y.Z-rc.N` (never `latest`, on Docker Hub too), npm dist-tag `next`.
